# Day 15 — User and Address Module Foundation

Day 15 starts User & Address from explicit ownership, business rules, and API contracts before persistence implementation. The purpose is to provide Order with stable customer and delivery-address dependencies without coupling Order to mutable profile data.

## Objectives

- [ ] Define the MVP User profile boundary; authentication credentials and authorization remain out of scope.
- [ ] Define Address ownership, validation, active/default state, and update/delete policy.
- [ ] Define minimal User and Address use cases and API contracts before entities or migrations.
- [ ] Preserve the decision that Order stores a delivery-address snapshot at creation time.
- [ ] Establish feature boundaries that can later be protected by Architecture tests.

## Scope and decisions

### User

- [x] Treat User as the customer profile and ownership boundary for personal contact data in the current MVP.
- [ ] Define required profile fields, uniqueness rules, lifecycle, and which fields are mutable.
- [ ] Introduce an `Email` Value Object to trim and normalize case, validate its format, and provide value-based equality.
- [ ] Keep `UserId` as `UUID` for now to match Catalog; defer typed IDs, `FullName`, and `PhoneNumber` Value Objects until they have clear rules or behavior.
- [ ] Exclude authentication credentials, roles, and authorization policy until their requirements are defined.

### Address

- [x] Make Address User-owned; a User may manage multiple addresses and select at most one default address.
- [ ] Define address fields, validation, active state, maximum count, and deletion behaviour.
- [ ] Define error cases for foreign ownership, inactive address selection, and default-address replacement/removal.

### Order dependency

- [x] Order stores a copy of delivery-address data rather than relying only on a mutable Address reference.
- [ ] Define the snapshot fields and the point at which Order copies them.
- [ ] Record the minimum User/Address data Order may reference for ownership and audit purposes.

## Architecture and API plan

- [ ] Create `user` and `address` feature packages with `domain`, `application`, `infrastructure`, and `presentation` layers.
- [ ] Define ports and use cases before persistence adapters; do not call another feature's repository directly.
- [ ] Decide whether Address remains a User-owned entity or becomes a separate aggregate after use-case review.
- [ ] Draft request/response DTOs, status codes, error codes, pagination, and ownership constraints.
- [ ] Add Architecture tests after the boundaries compile and stabilise.

## Execution order

1. [ ] Write the User profile and Address field/rule inventory, including concrete valid and invalid examples.
2. [ ] Define and test the `Email` Value Object before creating the User entity.
3. [ ] Define use cases: create/get/update User; create/list/update/delete Address; select default Address.
4. [ ] Draft API contract and error cases, then review it against the REST API checklist.
5. [ ] Create the feature package skeleton and ports; review dependency direction before JPA entities.
6. [ ] Create persistence models, migrations, adapters, and tests only after the contract is accepted.

## Expected outcome

- [ ] A reviewed User/Address contract exists in `docs/`.
- [ ] Ownership and default-address behaviour have unambiguous examples and error responses.
- [ ] Order can start later without placeholder fields or dependency reversal.
- [ ] The first implementation task has a clear boundary, test strategy, and Definition of Done.
