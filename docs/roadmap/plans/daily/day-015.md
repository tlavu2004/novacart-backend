# Day 15 — Multi-seller Product Names and Collision-safe Slugs

Day 15 adapts Catalog from the single-seller assumption that a product name is
globally unique to a multi-seller-ready model. Products may share a name, while
their public slugs remain globally unique and are allocated automatically.

This is an incremental Catalog change. It does not yet model seller ownership:
`seller_id` follows only after the User/Seller boundary, authentication, and
authorization rules are defined.

## Objectives

- [ ] Allow multiple Products to have the same case-insensitive `name`.
- [ ] Preserve a case-insensitive, database-enforced unique constraint for
  `products.slug`.
- [ ] Generate deterministic slug candidates such as `ao-thun-trang`,
  `ao-thun-trang-2`, and `ao-thun-trang-3`.
- [ ] Apply automatic slug allocation when creating a Product and when its
  name actually changes during an update.
- [ ] Handle concurrent create/update requests safely without exposing a
  normal slug collision to the API client.
- [ ] Keep the responsibility split consistent with Catalog Clean Architecture.
- [ ] Document the deferred decisions for product slug history and the User
  module.

## Slug allocation architecture

### Layer responsibilities

- [x] **Domain:** `SlugUtils` remains a pure deterministic utility. It
  normalizes a name to the base slug and may expose pure candidate construction
  (`base`, `base-2`, `base-3`, ...). Domain does not query persistence and does
  not own retry orchestration.
- [x] **Application:** introduce a shared application service, proposed name
  `ProductSlugAllocationService`. It is used by both create and update flows,
  chooses candidates through repository ports, and coordinates retries. This
  avoids duplicating the policy in `CreateProductUseCase` and
  `UpdateProductUseCase` without introducing an Infrastructure dependency into
  Domain.
- [x] **Infrastructure:** the persistence adapter persists and flushes each
  attempt. PostgreSQL's `uk_products_slug` unique index is the final source of
  truth under concurrency.

### Transaction-proxy structure

`REQUIRES_NEW` must be declared on a method of a separately injected Spring
bean. Calling an annotated method through `this` inside the same class bypasses
the Spring proxy and does not create a new transaction.

```text
CreateProductUseCase / UpdateProductUseCase
        │ inject
        ▼
ProductSlugAllocationService
        │ inject
        ▼
ProductSlugWriteAttemptService
  @Transactional(propagation = REQUIRES_NEW)
  persistCreateAttempt(...)
  persistUpdateAttempt(...)
```

- [ ] Keep `ProductSlugAllocationService` as the non-transactional candidate
  and retry coordinator.
- [ ] Implement `ProductSlugWriteAttemptService` as a distinct `@Service` and
  call it only through constructor injection; do not use `this.method(...)` or
  self-injection to invoke an attempt.
- [ ] Make each attempt method public and persist-and-flush inside its
  `REQUIRES_NEW` transaction.
- [ ] For an update retry, reload the Product and apply the full update command
  inside each attempt transaction so name/slug changes remain atomic with the
  rest of that update.

### Concurrent update decision

Slug retry alone does not protect a Product from unrelated concurrent updates.
Without versioning, reloading after a failed attempt can silently turn a stale
PATCH into last-write-wins behaviour; a concurrent deletion can also make a
later attempt disappear from the default soft-delete-restricted lookup.

- [x] Add optimistic locking before implementing retried Product updates:
  introduce a `version` column in the clean-database `V2` migration and map it
  with JPA `@Version`.
- [ ] Carry the version through the plain Product model/persistence mapper as
  concurrency state, without exposing JPA types to Domain.
- [ ] Make the Product update API supply the expected version. A stale version
  must return a deliberate conflict response; it is not a slug collision and
  must never enter the slug retry loop.
- [ ] Keep the original expected version across retry attempts. Each attempt
  reloads the Product inside its own transaction, verifies the expected
  version, and applies the complete PATCH command atomically.
- [ ] If the reload cannot find the Product because it was deleted by a
  concurrent request, return `ProductNotFoundException`; do not recreate it or
  retry a new slug.
- [ ] A concurrent change to an unspecified PATCH field is retained because
  the fresh Product is reloaded before the command is applied. A concurrent
  change to the same requested resource produces the optimistic-lock conflict
  instead of a silent overwrite.

### Allocation policy

1. Normalize the supplied name and generate the base slug.
2. Try the base candidate first.
3. If it is occupied, try monotonically increasing suffixes beginning at `2`.
4. For create, allocate a slug for every request.
5. For update, allocate a new slug only when the normalized incoming name is
   different from the Product's current name. Updates that do not change the
   name retain their slug.
6. Slugs are globally unique across all Products, not per seller.

The availability lookup is only an optimization. It must include soft-deleted
Products, or the database conflict path will repeatedly discover their reserved
slugs because the unique index includes soft-deleted rows while the default
Hibernate SQL restriction hides them.

`@SQLRestriction` is always appended by Hibernate to normal entity queries, so
the existing derived `existsBySlug` query cannot be reused for this purpose.
Add a narrow native query in `ProductJpaRepository`, exposed through the
adapter with a business-oriented name such as `isSlugReserved`:

```sql
SELECT EXISTS (
  SELECT 1 FROM products WHERE LOWER(slug) = LOWER(:slug)
)
```

- [ ] Use this native query only for reserved-slug allocation; it intentionally
  sees active and soft-deleted rows and matches the expression used by
  `uk_products_slug`.
- [x] Do not replace `@SQLRestriction` with a Hibernate `@Filter` in this
  change. A filter is dynamic but increases the risk that normal application
  queries accidentally include soft-deleted records.
- [x] Accept the PostgreSQL-specific native query trade-off for this one small,
  persistence-bound operation rather than leaking soft-delete mechanics into
  application code.

## Race-condition and transaction policy

An `existsBySlug` check cannot make allocation safe by itself: two requests can
observe the same candidate as free before either commits. Each candidate must
therefore be persisted and flushed before success is reported.

- [ ] Configure a bounded maximum retry count, initially in the range 20–50.
- [ ] Generate a new, higher suffix for every retry; never retry the identical
  candidate.
- [ ] Retry only when the exception chain identifies PostgreSQL SQLSTATE
  `23505` and constraint name `uk_products_slug`.
- [ ] Propagate all other integrity failures unchanged; specifically do not
  treat foreign-key, price, stock, or unrelated unique failures as slug races.
- [ ] Perform each write attempt in an independent transaction, proposed as a
  separate Spring bean with `REQUIRES_NEW`. A failed JPA flush can mark its
  transaction rollback-only, so catching and retrying inside the current
  transaction is unsafe.
- [ ] When attempts are exhausted, log a structured error and increment a
  metric, then throw `SlugGenerationFailedException` extending `BaseException`.
- [ ] Keep normal collision handling internal; `DataIntegrityViolationException`
  for `uk_products_slug` must not reach `GlobalExceptionHandler` during a
  successful retry sequence.

### PostgreSQL unique-violation classifier

There is no database-portable constraint-name API on Spring's
`DataIntegrityViolationException`. This application uses PostgreSQL, so keep
the driver-specific inspection isolated in Infrastructure, for example in a
`ProductSlugConstraintViolationDetector` used by the write-attempt boundary.

- [ ] Define the physical constraint/index name once, for example
  `PRODUCT_SLUG_UNIQUE_CONSTRAINT = "uk_products_slug"`, rather than repeating
  a string literal in retry code.
- [ ] Walk the complete `Throwable` cause chain from
  `DataIntegrityViolationException`.
- [ ] Retry only when a PostgreSQL `PSQLException` has SQLSTATE `23505` and
  `getServerErrorMessage().getConstraint()` equals the declared slug-unique
  constraint name.
- [ ] Optionally recognize Hibernate's intermediate
  `org.hibernate.exception.ConstraintViolationException` when it exposes the
  same constraint name, but do not retry when the PostgreSQL cause cannot be
  positively identified.
- [ ] Treat every other exception shape, SQLSTATE, or constraint name as a
  non-retryable failure. This preserves foreign-key, CHECK, optimistic-lock,
  and unrelated unique-constraint errors.

### Maximum slug length

`products.slug` is `VARCHAR(255)`. A normalized base slug can already consume
all 255 characters, so appending `-2` or a later suffix must reserve length
before candidate construction.

- [ ] Define `MAX_PRODUCT_SLUG_LENGTH = 255` and keep it aligned with the
  migration and JPA column mapping.
- [ ] Reject a name whose normalized base slug is empty; for example, a name
  containing only punctuation currently has no usable slug.
- [ ] Build the base candidate with at most 255 characters. For suffix `-n`,
  truncate the base to `255 - suffix.length()` before concatenating the suffix.
- [ ] Never truncate the completed candidate, because that could remove the
  suffix and repeat a previous candidate.
- [ ] Cover a 255-character base, suffixes with multiple digits, and an empty
  normalized base in unit tests.

## Product code impact

### Application and exceptions

- [ ] Remove name-uniqueness checks from `CreateProductUseCase`.
- [ ] Replace its direct duplicate-slug rejection with slug allocation and
  conflict-safe persistence.
- [ ] Update `UpdateProductUseCase` to compare the incoming normalized name
  with the existing name before regenerating a slug.
- [ ] Remove `DuplicateProductNameException` and assess removal/deprecation of
  `CatalogErrorCode.PRODUCT_ALREADY_EXISTS` (`PROD_001`) after API-client
  compatibility review.
- [ ] Stop using `DuplicateProductSlugException` for ordinary collisions; use
  the new failure exception only after retry exhaustion.
- [ ] Review the HTTP error mapping for the new `BaseException` subtype and
  ensure an unexpected `DataIntegrityViolationException` remains visible as an
  operational error rather than being incorrectly retried.

### Repository and persistence ports

- [ ] Remove `existsByNameIgnoreCase` and
  `existsByNameIgnoreCaseAndIdNot` from the Product repository port,
  persistence adapter, and Spring Data repository.
- [ ] Provide a slug-availability query that can see soft-deleted rows, or
  otherwise make the allocator's candidate lookup explicitly bypass the
  default SQL restriction.
- [ ] Ensure the write path flushes before returning from an allocation attempt
  so a unique-constraint collision is caught in that attempt.
- [ ] Keep Product name search/filter behaviour; the replacement name index is
  for search/query performance, not uniqueness validation.

## Deferred User module proposal

The User module remains unstarted. Its initial authentication target is login
by username, email, or phone plus password, with a future OAuth-account linking
extension.

### Proposed tables

- [ ] `users` — stable account identity and lifecycle state.
- [ ] `user_identifiers` — username, normalized email, and normalized phone;
  enforce global uniqueness on `(type, normalized_value)`.
- [ ] `user_credentials` — one-to-one password credential and password hash
  metadata; never store plaintext passwords.
- [ ] `user_profiles` — optional profile data separated from authentication
  state.
- [ ] `roles` — defined roles such as buyer, seller, and admin.
- [ ] `user_roles` — many-to-many assignment between users and roles.
- [ ] `oauth_accounts` — add when OAuth linking is implemented rather than
  creating unused schema now; it should associate a provider and provider
  subject with a User.

### Decisions required before User SQL

- [ ] Confirm the final User table list and whether role data should be a
  normalized RBAC model (`roles` plus `user_roles`) or a simpler enum while the
  role set is fixed.
- [ ] Define identifier verification, password reset, account lockout, and
  uniqueness/canonicalization rules for email and phone.
- [ ] Define seller onboarding and whether every seller is a User role or a
  separate Seller business profile.
- [ ] Define OAuth provider/subject uniqueness and account-linking security
  rules before adding `oauth_accounts`.
