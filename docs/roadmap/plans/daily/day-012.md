# DAY 12 — Catalog testing

This plan covers the Catalog module (`Category` and `Product`) and follows the
order used in the repository: isolated logic first, then application behavior,
persistence, HTTP, and finally full application workflows.

## Learning

### Testing fundamentals

- [x] Test pyramid: unit tests are the fastest and most isolated; slice tests
  and integration tests are fewer and slower; E2E tests are the smallest layer.
  A practical starting heuristic is roughly 70% unit, 20% integration/slice,
  and 10% E2E, but behavior and risk matter more than a fixed ratio.
- [x] Test doubles: mocks verify interactions, stubs provide canned answers,
  and fakes provide a lightweight working implementation; use the simplest
  double that preserves the behavior the test needs.
- [x] AAA pattern (Arrange–Act–Assert).
- [x] Test naming that describes the condition and expected behavior.

### Spring test slices

- [x] `@DataJpaTest`: loads the JPA slice (entities and repositories), not the
  complete application; PostgreSQL Testcontainers is used instead of H2 for
  PostgreSQL-specific behavior.
- [x] `@WebMvcTest`: loads the MVC/controller slice and mocks application
  dependencies.
- [x] `@SpringBootTest`: loads the full application context for real
  application integration tests.
- [x] Testcontainers: provides an isolated PostgreSQL instance matching the
  production database engine more closely than H2.
- [x] Testcontainers lifecycle: one shared PostgreSQL container is kept alive
  for the test JVM so cached Spring contexts do not use a stopped container.

### Mockito

- [x] `@Mock` creates a test double; `@InjectMocks` constructs the subject and
  injects its mocked dependencies.
- [x] `when(...).thenReturn(...)` stubs behavior; `verify(...)` checks
  interactions.
- [x] `ArgumentCaptor` captures an argument when its exact value must be
  inspected; typed matchers are preferred when a captor would require an
  unchecked generic cast.

## Knowledge to retain

### Testing

- [x] Unit tests should be fast and isolated; integration tests may be slower
  because they verify real framework/database behavior.
- [x] Understand that a transactional test method is normally rolled back
  automatically after the method, and when API workflows need explicit
  isolation or unique data instead.
- [x] Keep each test independent of another test's data or execution order.

### Mockito

- [x] Mocking a repository interface keeps application unit tests isolated from
  persistence implementation details.
- [x] Do not mock simple value objects, DTOs, or domain entities unnecessarily.

### Testcontainers

- [x] Understand container startup, reuse within the test JVM, and cleanup by
  Testcontainers/Ryuk.
- [x] Understand the difference between the manually managed `postgres-test`
  service from Day 11 and an ephemeral PostgreSQL container created by tests.

## Optional follow-up quality gates

These are intentionally not required for the current backend-only merge.
They become implementation work only when their adoption conditions are met.

- [ ] Architecture tests (for example, ArchUnit) when Catalog service
  extraction begins. Do not add them in the current testing PR. Before writing
  a rule, complete this extraction checklist:
  - Define the target boundaries: domain must not depend on application,
    infrastructure, or presentation; application depends on domain and ports;
    infrastructure implements ports; presentation invokes application use
    cases without accessing infrastructure directly.
  - Inventory current cross-layer dependencies, including application use of
    infrastructure utilities/specifications, application use of presentation
    request DTOs, and exception inheritance across domain/application/shared
    packages.
  - Decide each dependency's target: move a shared abstraction to domain or
    application, introduce an application input model/port, or keep it only
    with an explicit temporary exception and removal task.
  - Refactor the selected dependencies until the intended boundaries compile.
  - Add ArchUnit rules that enforce the target boundaries and any explicitly
    approved temporary exceptions; do not encode today's accidental imports as
    permanent architecture.
  - Make these rules required in `mvn verify` and CI before the Catalog module
    is extracted into its own repository/service.
- [ ] API contract tests when an OpenAPI document or another machine-readable
  contract is versioned, or when an external client depends on it. The `/api/v1`
  URL prefix versions routes, but it is not itself a versioned API contract.
- [ ] Security tests when authentication and authorization are introduced with
  a defined role/permission matrix and at least one protected endpoint.
- [ ] Performance/load tests when an SLA, latency budget, throughput target, and
  production-like data profile exist; define measurable pass/fail criteria
  before selecting a load-testing tool or writing a scenario.
- [ ] End-to-end tests when a frontend or external integration exists.
  Add a real cross-system user journey as the test target, rather than a
  duplicate of the backend integration suite.
- [x] CI verification on a clean runner with a Docker/Testcontainers-compatible
  runtime: both the GitHub Actions push and pull-request runs passed without a
  manually configured PostgreSQL database.
