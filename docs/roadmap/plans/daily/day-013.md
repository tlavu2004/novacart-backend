# Day 13 — Separate Domain and Infrastructure Entities and Mapping

Day 13 refactors Catalog so Domain no longer depends on JPA, Hibernate, or Spring Data. Persistence entities live in Infrastructure; Domain keeps `Category` and `Product` state and business behaviour. MapStruct maps the two models, and each query has a deliberate fetch plan to prevent lazy-loading failures and N+1 queries.

## Objectives

- [x] Keep Domain entities free of JPA/Hibernate/Spring Data annotations and types.
- [x] Keep JPA entities, Spring Data repositories, and Specifications in Infrastructure.
- [x] Make the persistence adapter the only Domain-to-JPA mapping boundary.
- [x] Keep creation rules explicit and preserve business behaviour during persistence mapping.
- [x] Configure compile-time MapStruct mapping with strict unmapped-field handling.
- [x] Keep controllers and Presentation away from JPA entities and lazy proxies.
- [x] Preserve the public API, Flyway schema, and existing business behaviour.

## Architecture decisions

### Domain and persistence models

- [x] `Category` and `Product` are plain Java Domain entities; repository interfaces are Domain/Application ports.
- [x] `CategoryJpaEntity` and `ProductJpaEntity` own table/column mapping, constraints, auditing, soft-delete restriction, enum mapping, foreign keys, and ORM relationships.
- [x] Repositories and use cases exchange Domain models only; JPA `Page`, `Specification`, `JpaRepository`, and JPA entities do not cross the boundary.
- [x] `Category` does not own a Product collection: no Catalog use case needs the bidirectional object graph.
- [x] `Product` keeps a Domain reference to Category for create/update and API response needs, not as an ORM concern.

### Factories and mapping

- [x] `Category.create(...)` sets its default active state and `Product.create(...)` sets `DRAFT`.
- [x] Business updates use named methods for name/slug, description, price, stock, category, status, and soft delete.
- [x] MapStruct maps `JpaEntity ↔ Domain` inside persistence mappers with `unmappedTargetPolicy = ERROR`.
- [x] Rehydration-specific APIs are unnecessary while Domain and persistence state remain one-to-one.

### Lazy loading and query contracts

- [x] Relationships remain `LAZY`; Open Session in View is disabled.
- [x] Product detail and list queries load Category through `@EntityGraph`; the relation is to-one, so pagination remains safe.
- [x] Category deletion uses an existence query instead of loading all Products.
- [x] Integration tests verify response serialization and query counts for product detail/list, protecting against lazy-loading and N+1 regressions.
