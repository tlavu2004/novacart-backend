# Day 14 — Catalog Review, Architecture Checklist, and Next-Module Preparation

Day 14 hardens the Catalog module after the previous implementation days. The goal is to turn architectural and API practices into repeatable checks, record decisions, and prepare a safe foundation for the next module.

## Objectives

- [x] Review Catalog business flows, architecture, and code quality end to end.
- [x] Separate `Category` and `Product` into independent feature boundaries without breaking required API contracts.
- [x] Publish a reusable Clean Architecture checklist for later modules.
- [x] Publish a reusable REST API design checklist for current and future APIs.
- [x] Add minimal Swagger UI/OpenAPI for Catalog contract review.
- [x] Bring CI/CD close to merge-ready quality gates.
- [x] Record the TD-14 Domain-setter decision as an accepted MapStruct direct-mapping trade-off, with a defined revisit trigger.
- [x] Start **User & Address** before Order, so identity and delivery-address dependencies are explicit first.

## Catalog review scope

### Business flows and tests

- [x] Inventory Category and Product use cases: create, detail, list/filter/sort/page, update, category move, status update, stock update, and soft delete.
- [x] Verify validation, business rules, and error responses are consistent in every use case.
- [x] Verify status transitions, non-negative stock, valid price, slug rules, and protected category deletion remain covered by tests.
- [x] Confirm refactors did not unintentionally change the API contract.

### Persistence and performance

- [x] Verify pagination, sorting, name search, category filtering, and combined queries. `page` is zero-based; default `size` is `20`, maximum is `100`.
- [x] Escape `%`, `_`, and `\` in product name search so they are treated as literal input.
- [x] Protect pagination/search behaviour with controller, repository, and integration tests.
- [x] Review query plans and indexes with `EXPLAIN ANALYZE`. `idx_products_category_id` serves category filtering and product-usage checks; no speculative index was added.
- [x] Record that contains search currently uses a sequential scan; evaluate a GIN/trigram index only with production-like workload evidence.

## Category and Product feature boundary

- [x] Inventory packages, use cases, ports, adapters, controllers, DTOs, mappers, repositories, and tests shared by Category and Product.
- [x] Separate feature packages into `domain`, `application`, `infrastructure`, and `presentation` layers.
- [x] Keep Product as the owner of the Category reference for create and category-move use cases; do not introduce an unnecessary Category-to-Product collection.
- [x] Use `CategoryProductUsagePort` for Category deletion validation, removing the bidirectional repository dependency.
- [x] Keep JPA entities, Spring Data repositories, and persistence mappers within the owning feature's Infrastructure layer.
- [x] Update DI, component scanning, and test packages after the split.
- [x] Add ArchUnit to `mvn verify` to enforce Domain isolation, Application/Presentation-to-Infrastructure direction, and the Category Application boundary.
- [x] Separate the plain Domain status-transition exception from the Application exception that owns `CatalogErrorCode` and HTTP-facing error semantics.

## API design and delivery

### Swagger UI and OpenAPI

- [x] Add OpenAPI/Swagger UI compatible with the current Spring Boot version; expose the UI locally only.
- [x] Expose Catalog paths in the generated OpenAPI specification and set API metadata to `NovaCart API` version `v1`.
- [x] Keep Swagger UI disabled by default, so production runtime behaviour is unchanged unless explicitly configured.
- [x] Version the generated OpenAPI contract as `v1` and add an integration contract test for important Catalog paths (TD-03).

### CI/CD

- [x] Run build, unit tests, integration tests, Flyway/schema validation, and the existing coverage gate in CI through `mvn verify`.
- [ ] Add static analysis, format, or lint checks after choosing and baselining an appropriate tool.
- [x] Cache Maven dependencies, upload Surefire/JaCoCo reports, and cancel superseded CI runs for the same branch.
- [x] Require a green pipeline before merge through an active GitHub ruleset: pull request, `Verify tests and coverage`, up-to-date branch, deletion restriction, and force-push blocking.

## Next module: User and Address

Choose **User & Address** before Order. Order needs an actor, contact details, delivery addresses, address-selection rules, and a decision about historical delivery data.

- [x] Decide whether User is an identity/profile concept or only a customer-domain concept in the current scope.
- [x] Define Address ownership, maximum count, default-address behaviour, and update/delete rules.
- [x] Decide whether Order references User/Address or stores an address snapshot; default to a snapshot for historical delivery accuracy.
- [ ] Define minimal use cases and API contracts before creating entities or persistence models.
- [x] Record remaining Order dependencies in the roadmap once User & Address boundaries are stable.
